## 1. 首问 keyed 召回（A）

`src/retrieve/query-recall.ts`（新增）+ `src/index.ts` 注入段。

- 触发：`step === 1` 或压缩后重注入；同一 agent 每会话一次。
- 文本门：先确认确有用户文本（占位句跳过）→ CJK ≥6 字 / 其他 ≥20 字符 → 非寒暄。
- 检索：`user` 恒查，有 cwd 且项目库已存在才查 `project`；两库 `Promise.allSettled`，单库失败只丢那一库；检索词截 80 字符；整段 80ms 上限（同步 SQL 期间该上限只是建议值，注释写明）。
- 过滤：与常驻画像同口径——`expiresAt` 过期丢弃、`sourceTier ∉ injectTiers` 丢弃。
- 渲染：`<memory_context>` 内置一小节，行格式 `- [kind] 内容（scope/#前8位）`；块内给 `batchId` 与「evidenceRefs 用行内 ref」；块尾提示 `kyzmem_examine ids=[短 ref]`（不再列 36 位 UUID）。
- 副作用：`search` 传 `touch:false` / `auditMode:'query-recall'` / `auditQuery:'hash'`（首问原文不进 op_log）；只对**实际注入**的 id 调 `markRetrieved`（提 `last_retrieved_at` 与 confidence，不动 `access_count`，避免"被召回一次就免疫衰减"）。
- 可观测：每个分支写 `op_log('query-recall', {outcome, chars, tookMs, top, ids, batchId?})`，outcome ∈ `injected|no-hit|timeout|budget-skip|error|no-text|off`。
- 配置：`queryRecall`（off/light/full，默认 light）、`queryRecallBudget`（默认 600，[240,4000]）、`queryRecallTop`（light 3 / full 5）。600 的取值依据：zh 3 条 449、en 3 条 558、ru 3 条 578 字符。

## 3. 评审与修复（本轮最有价值的部分）

两路独立评审共提出 3 个 P1 + 20 余条 P2，修复后提交 `f74e2d8`。关键几条：

| 评审发现 | 修复 |
|---|---|
| **协议标签逃逸**：记忆正文含孤立 `</kyzmem_memory_context>` 时，渲染出的块 1 开 2 闭，闭标签后的文本落到块外，可伪造包外指令 | `sanitizeProtocolText` 改为「成对剥离 → 残留标签中和（`<`→全角 `＜`）→ 归一空白」，覆盖 6 个协议标签的 7 种写法；不再从标签起点截断正文（旧行为会丢内容） |
| 召回不筛来源分级与 TTL，网页/工具输出内容可在开场被推送 | 与画像同口径过滤 |
| 召回的 `batchId` 没有给模型，下一步却提醒"用 batchId 调 assess"，批次永远悬空 | 块内带 `batchId` + ref 说明；`rememberCitationRefs` 打通引用强化 |
| 模型看到两套 id（行内 ref / 提示里的完整 UUID），抄哪套都有一半机会被拒 | 只保留短 ref，`kyzmem_examine` 支持完整 UUID / 8 位前缀 / `scope/#8` ref 三种形态 |
| `store.search` 会强化 top-N **候选**（即使只有 1 条被注入），并让条目免疫衰减 | `touch:false` + 只对注入项 `markRetrieved`（不动 access_count） |
| 首问原文（≤200 字、未脱敏）被写进 op_log | 自动召回只落 `queryHash` 前 16 位 |
| 默认预算只装 1–2 条 | 默认 600；测试钉住默认下真得 3 条 |
