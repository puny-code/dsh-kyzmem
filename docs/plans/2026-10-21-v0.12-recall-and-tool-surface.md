- 配置：`queryRecall`（off/light/full，默认 light）、`queryRecallBudget`（默认 600，[240,4000]）、`queryRecallTop`（light 3 / full 5）。600 的取值依据：zh 3 条 449、en 3 条 558、ru 3 条 578 字符。

## 6. 第二批：文件锚（C，schema v16）与 `[RESUME]`（D）

方案 §6（C）与 §7（D，原计划 v0.12.1 / v0.13，本批合并落地）。落点：

### 6.1 文件锚（C）

| 环节 | 落点 |
|---|---|
| schema | `SCHEMA_VERSION = 16`；`MIGRATIONS['15']` 加 `anchor_path` / `anchor_hash` / `anchor_checked_at` 三列 + `nodes_anchor` 索引；新建库建表 SQL 直接含三列 |
| 类型 | `MemoryRecord.anchor?: { path, hash, checkedAt }`（`src/types.ts` 的 `MemoryAnchor`）；缺省不写对象键 |
| 写入 | `kyzmem_save` / `kyzmem_update` 新增 `anchor`（工作区相对路径）；`hash = sha256(mtimeMs + ':' + size)` 前 16 位，**不读文件内容**；文件不存在则不写锚点、结果里提示 |
| 复验 | `src/anchor.ts`：`normalizeAnchorPath`（拒绝对路径三种形态与 `..` 逃逸）、`computeAnchor`、`checkAnchor` 三态、`checkAnchors`（一次渲染最多 8 条，各 stat 一次） |
| 渲染 | `kyzmem_search` / `kyzmem_examine` 行上标注：`[锚点丢失]` / `[可能过期]`；一致不标；**不影响排序**（第一版不降权） |
| 往返 | `exportAll`（经 `rowToRecord`）+ `sqlImportInsert` 28→31 列，导入导出保留锚点 |

`kyzmem_update` 的锚点继承语义：显式给 = 按新路径重算；`null` = 明确清空（换了文件而这个路径又不存在）；
缺省 = 继承旧锚点且**不刷新** `checkedAt`——写入不等于复验过，刷新它会让面板的 stale 统计失真。

### 6.2 为什么不做 refurb anchor 任务（方案 §6「后台」那段没做）

方案原本写「refurb 任务加一档 `anchor`，批量复验最近 N 条，变旧的写 `op_log op='anchor-stale'`」。**没有做**，理由是三条实测与一条语义：

1. **实时 stat 已经是权威**。渲染路径上每条本来就要 stat 一次（有界 8 条），结果直接贴在模型看的那一行上；
   后台批量复验得到的结论更旧，还要多一张「上次复验时刻」的表——它回答的问题（这条新不新）
   在渲染时被问一次就够了，问两次只会让两个答案打架。
2. **预算账不划算**。`maintenanceBudgetItems` 缺省 50 条，而个人库 active 中位数在百条量级：
   一轮 refurb 只能覆盖一部分条目，`anchor-stale` 计数因此既不实时也不完整——用它算 §9 的
   「stale 命中率」等于用抽样当全量。
3. **写入期台账一旦建了就得维护**。`anchor_checked_at` 现在只在写入时落一次（渲染期复验只读不写，
   原因见上：写 `checked_at` 需要把「展示」变成「写库」，而展示路径是并发只读的）。
   真要恢复它，正确形态是把复验挪到后台 worker 并让渲染只读缓存——那是另一件事，
   要连带改 `stat` 的并发上限与一致性，不该顺手塞进 refurb。
4. **语义上锚点已经自证**。`missing` / `stale` 两个标记都由「当前文件状态 vs 入库指纹」当场得出，
   不依赖任何后台推进；后台任务唯一能多给的是「没人看的时候也扫一遍」，而没人看的时候
   这个标记也没有读者。

保留 `anchor_checked_at` 列与渲染期只读复验，等 §9 的 stale 命中率真的需要全量基线时，
再按上面第 3 条的形态（后台 worker + 渲染只读）补，而不是把写入期台账当调度器用。

### 6.3 `[RESUME]` 恢复简报（D）

- 数据：`KyzmemStore.latestSessionSummary()`（`ORDER BY updated_at DESC, rowid DESC LIMIT 1`），
  project 库先探存在（复用 `openProjectStoreIfExists`，不为一次性 cwd 建空库）。
- 注入：`step === 1`（或压缩后重注入）且 `resolved.resumeBriefing` 且有摘要时，在画像**之前**插一段：
  `[RESUME] 上次会话（{日期}）：{摘要 ≤120 字}` + `今日待回忆 N 条`（复用 due 计数）+ `上次未完成摄取 M 条`（`op_log('ingest-pending')` 未清数，读不到就省）。整块硬上限 `resumeBriefingChars`。
- 门：同一会话一次；压缩后允许再一次（与画像/首问召回同一判据）。摘要被清洗成空串时不消耗机会。
- 预算收缩顺序：先压摘要（下限 24 字）→ 再丢计数行（后加的先生）→ 最后硬截断。
- 配置：`resumeBriefing`（默认 true）、`resumeBriefingChars`（默认 200，[80,600]）。
- 项目库开库预算 `RESUME_PROJECT_OPEN_MS = 500`：200ms 时简报随机缺席（实测 3 条挂 2 条），
  因为冷启动还压着旧库导入/迁移检查；500ms 是「一次会话只付一次」的上限，不是延迟目标（热路径 8–30ms）。

### 6.5 已知边界（写在这里，避免以后当成已完成）

- 真机 `user.db` 迁移已在副本上验证：v14 → v16（跨 v15、v16 两次迁移），30 条 → 30 条，kind 分布、
  排序样本、FTS 30 行全部不变，0 条带锚点（功能上线前没有锚点数据）。
- 跨工作区检索的锚点：`search` 可能命中别的项目存的条目，其相对路径会按**当前**会话 cwd 解析，
  于是可能把「另一个工作区里的同名文件」当成本条目的锚点。第一版接受这个偏差（标注只提示不定罪），
  真要修得把工作区标识一起存进锚点。
- 面板还没有消费 `anchor` 字段（`MemoryRecord` 上已经带着它，路由未透出）。
- `kyzmem_distill` 的 `supersedeMany` 不继承锚点：蒸馏把多条记忆并成一条，源锚点可能互不相同，
  第一版选择「不猜」——新条目没有锚点，旧条目的锚点随归档保留。要在蒸馏路径上带锚点，
  得先定义「多个源文件怎么变成一个锚点」，那是另一个设计问题。
- 自动摄取（`ingest`）不写锚点：摄取期没有可靠的「这条记忆对应哪个文件」信号，
  只能靠模型显式调用 `kyzmem_save ... anchor=`。

## 7. 第三批落地（E 采纳加权 + R5 度量 + 面板指标）

**E 采纳率进排序**：`store.adoptionStats()` 扫最近 500 条 `recall-used|recall-ignored` 的 `detail.ids`，
每 store 实例缓存 60 秒（不共享模块级缓存——一个进程同时开 user/project/shared，共享会串味）。
因子 `1 + min(0.1, w·(used+1)/(used+ignored+2))`，`used<=0` 恒为 1：只奖励被采纳过的条目，
忽略只做分母不产生负分，上限 +10% 防「越被召回越被召回」的反馈环。
实测 3 次采纳约 +4%，足以翻过 1/61 与 1/63 的 RRF 差；「展示 23 次只用 3 次」只剩 +0.8%，翻不动。
`rankAdoptionWeight` 默认 0.05，`RankBoostOptions.adoptionWeight` 缺省 0（直连库的脚本与旧测试语义不变）。

**R5 六项度量的口径**（缺数据一律 undefined，面板显示 `—`，路由全程不抛）：
- `injectionCount` / `exposureChars` / `tokenCostEstimate`：按「一次 query-recall 注入 → 下一条注入」切段，
  该段后续 op_log 行数当请求数上界，`chars × max(1, 行数)` 是偏保守的估算；token 复用 `estimateTokens`。
- `activationRate`：注入后同段出现 `examine` 或 `recall(mode='search')` 的注入点占比。
- `drillDownRate`：`examine` 次数 / `recall(mode='search')` 次数。为让分子有数，`kyzmem_examine`
  成功返回后按 scope 各写一条 `examine` 审计（detail.ids），与 recall 审计同粒度。
- `staleAnchorRate`：每库抽样至多 40 条带锚条目，实时 `mtime:size` 比对；推不出工作区根就不算该项。

**面板**：运维页指标表 12 → 18 项（新增注入曝光字符、首问注入次数、激活率、下钻率、注入 token 成本、
锚点过期率），`compactCount` 紧凑格式（1.2M / 34K），缺失显示 `—` 并把精确值放进 `title`；
三语各补 6 个键，`KyzmemKey` 联合类型保证编译期齐平；未新增视图或 tab。

## 8. 两轮只读评审（质量 / 风险）的结论与处置

第二轮加了两个只读评审代理，分别看「第二批（C+D）」与「第三批（E+R5+面板）」。两轮都是 P1=0。

**已修（随本版）**
- 下钻率口径：原来 `indexSearches>0 && examineRuns>0` 才给值，导致「检索多次、一次没下钻」被显示成 `—`（读成「还没开始测量」）。
  改成只有分母为 0 才缺省，分子 0 就是真实的 0%；`tests/telemetry.spec.ts` 与 `tests/routes.spec.ts` 的旧前提断言同步改掉。
- `kyzmem_examine` 补写 `examine` 审计（按 scope 各一条，`detail.ids`），R5 的 `drillDownRate` 因此有分子。

**记录不改（有意的取舍）**
- 锚点只存相对路径、不存工作区归属：`user`/`shared` 库里的锚点换个工作区打开会被标「锚点丢失」。
  这是**误标而非误判数据**——标注只提示不定罪，且方案 §6.5 已写明。要修得给锚点加 root 字段（schema v17），
  属于跨项目语义设计，留到下一版。
- `adoptionFactor` 的 `used<=0 → 1`：让「从未被采纳」与「展示了但全被忽略」同权。这是「只加不减」的刻意选择，
  避免反馈环把新条目直接压死；代价是忽略只在已有采纳史之后才起作用。
- 重复 id 不去重（`detail.ids` 里同一条出现两次算两次采纳）、`/stats` 的 40 条实时 stat 在慢盘上会拖慢面板轮询、
  俄语 token 成本按拉丁样本高估约 1.6×：都是已知的估算误差，记在这里而不是加代码兜底。
